= Putting Guardrails to Work – Workload Hardening (Custom SCC, Seccomp, SELinux)
:role: Intermediate Runtime Security
:skills: SCC Hardening, Capability Reduction, seccomp, SELinux Contexts
:mitre: T1611 (Escape to Host), T1068 (Privilege Escalation), T1548 (Abuse Elevation Control Mechanisms)
:compliance: NIST 800-53 CM-6 / SC-7, CIS Kubernetes 5.x, ISO 27001 A.12, PCI DSS 6.5
:labid: LAB-201-02

**Duration:** ~25 minutes

== Overview
You’ll author and apply a hardened SecurityContextConstraints object, combine it with seccomp and SELinux context discipline, and prove it works through positive and negative deployment tests.

Harden a workload with a custom SCC where needed, plus seccomp and SELinux controls, and verify the pod still runs under stronger constraints.

== Why it matters
Default settings are like issuing every warehouse worker a multi‑tool with blades, saws, and pry hooks when they only needed a flat screwdriver. Extra capabilities become unintended weapons if someone misuses or compromises the account. Hardened runtime boundaries (SCC + seccomp + SELinux) strip the “just in case” powers that attackers love to discover after a simple pod foothold. 

End goal is a lower chance a minor pod compromise escalates into node‑level panic, plus clearer evidence of least privilege for auditors.

== What does it solve
Broad SCC usage silently enables:

* Leftover Linux capabilities (each one is an exploration vector)
* Accidental root UID usage (scripts work as root, drift ignored)
* Looser SELinux contexts (more permissive file/process access)
* Unfiltered syscalls (toolbox open for exploitation chains)

== Your Mission
Prove restricted-plus is not enough for this workload: apply a tighter SCC, run a good pod, then watch capability-add and root-UID pods fail.

== Debrief

Hardened SCC, seccomp, capability drops, and SELinux close gaps that restricted defaults alone leave for sophisticated workloads.

What breaks without this:

* Leftover capabilities / loose syscalls → privilege escalation after container compromise
* Invented custom SCCs everywhere → unmaintainable exception sprawl

[IMPORTANT]
====
Treat a custom SCC as an exception, not a platform default. Start from `restricted` / `restricted-v2` (xref:101-04-scc-resource-guardrails.adoc[101-04]). Rebuild the image when the app wants root, extra caps, or a privileged port (xref:101-11-rebuilding-images.adoc[101-11]). Only author a tighter SCC—like `hardened-nonroot`—when a named workload still needs a narrower UID range, volume list, or capability set than restricted already provides, and bind `use` to that project's service accounts only.

Layer the runtime controls instead of stuffing everything into the SCC:

* *Capabilities:* `requiredDropCapabilities: ["ALL"]`, then add back only what the process has proven it needs.
* *seccomp:* pin `runtime/default` at minimum; use the xref:101-10-security-compliance-addons.adoc[Security Profiles Operator] when you need a recorded, workload-specific profile.
* *SELinux:* keep `MustRunAs` (MCS labels). Do not relax to `RunAsAny` to silence a volume-permission failure.
* *Drift:* RHACS (xref:acs-06-network-and-runtime.adoc[runtime policies]) should flag new `capabilities.add`, `privileged`, host mounts, and SCC annotation changes so a cluster-admin create does not silently bypass the exception you just designed.
====

[NOTE]
====
If the workload already runs under restricted after an image fix, stop there. A second SCC is another cluster-scoped object to bind, audit, and forget. The sprawl mode is a new SCC per team “because production is special,” which becomes an unreviewable allow-list.

Watch for drift after the exception ships: a later Deployment bump that adds `NET_RAW` or `runAsUser: 0` will succeed if the creator can use `privileged` (as `lab-user` just did without `--as`). Continuous detection—ACS policy, admission (xref:201-10-admission-governance.adoc[201-10]), or a Compliance Operator check—is what keeps the deny you demonstrated from rotting.
