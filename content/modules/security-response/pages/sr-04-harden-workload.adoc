== Overview

The next morning Morgan asks Sarah to show that image hardening would have limited a real vulnerability in ACME's Socket.IO workloads.

CVE-2025-61765 affects `python-socketio` before 5.14.0. When several servers share a message broker, the library unpickles broker messages. Untrusted data in that path can cause the process to run a command. The published condition for that command path is a shell inside the image. A distroless runtime image has no shell, so the same condition cannot start `/bin/bash`.

This exercise does not run an exploit. You inspect the vulnerable deployment, compare the two Containerfiles, and roll out the hardened image that is already built for this lab.

== Your mission

See the CVE on the running Socket.IO deployment, then replace it with `quay.io/smileyfritz/socketio-server:0.1.0-hardened`.

.See what RHACS reports
[%collapsible]
====
. In RHACS, open *Vulnerability Management*.
. Filter to namespace `vulnerable-workload-{workshop_user_suffix}` and deployment `socketio-server`.
. Review the critical and important findings, including `python-socketio`.
====

.List the demo pods
[%collapsible]
====

----
oc get pods -n vulnerable-workload-{workshop_user_suffix} -o wide
----

Expect `message-broker`, `socketio-server`, and `edge-server`.

====

.Compare the Containerfiles
[%collapsible]
====
The vulnerable image starts from UBI Python, which includes a shell and package tools, and pins the affected library:

[source,dockerfile]
----
FROM registry.redhat.io/ubi9/python-311
----

[source,text]
----
python-socketio==5.13.0
----

The hardened build installs dependencies in a builder stage, then copies the virtualenv onto a Red Hat Hardened Images Python runtime. That runtime stage has no shell. The hardened requirements file does not pin `python-socketio`, so a rebuild takes a current release:

[source,dockerfile]
----
FROM registry.access.redhat.com/hi/python:latest-builder AS builder
# pip install from requirements-hardened.txt

FROM registry.access.redhat.com/hi/python:latest
COPY --from=builder /opt/venv /opt/venv
----

Both Containerfiles are in `vendor/security-response/data/security-new/setup/exercise4/socketio-server/` if you want the full files. The lab does not build them. The next step applies the prebuilt hardened deployment.

image::fsi-security/hardened-image.png[Hardened image,link=self, window=blank, width=100%]
====

.Roll out the hardened deployment
[%collapsible]
====
[source,bash,subs="+macros,+attributes",role=execute]
----
export NAMESPACE=vulnerable-workload-{workshop_user_suffix}
cd ~/ocp5-rhacs-showroom
envsubst < setup/exercise4/k8s/socketio-server-hardened.yaml | oc apply -f -
oc -n "$NAMESPACE" rollout status deploy/socketio-server
oc -n "$NAMESPACE" get deploy socketio-server \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
----

The image line should be `quay.io/smileyfritz/socketio-server:0.1.0-hardened`.

image::fsi-security/hardened-image-running.png[Hardened socketio-server running,link=self, window=blank, width=100%]
====

.Confirm the running container has no shell
[%collapsible]
====
[source,bash,subs="+macros,+attributes",role=execute]
----
export NAMESPACE=vulnerable-workload-{workshop_user_suffix}
if oc -n "$NAMESPACE" exec deploy/socketio-server -- /bin/bash -c 'echo shell-present'; then
  echo "Shell is still present. The hardened image is not the one running."
else
  echo "No shell in the running socketio-server container."
fi
----

You want the second message. The library defect can still be present in an image. Removing the shell is the control this rollout puts in place.
====

== What you learned

* RHACS ties CVE-2025-61765 to the running `socketio-server` deployment.
* The hardened runtime image removes the shell that the command path needs.
* Swapping the broker to a Red Hat image is a separate supply-chain decision from the application runtime.
